## 实现思路与关键取舍

用户描述需求后，Mike 协调任务，Emma 提出验收要求，Bob 规划文件，Alex 编写与检查代码。后端使用 **Vercel AI SDK 的 ToolLoopAgent**：四个角色分别拥有独立上下文、工具与停止条件，可以根据工具反馈继续行动。新建应用必须先有需求与计划，小改动可以只调用 Mike 和 Alex。

Alex 先修改候选文件，静态检查失败时继续修复；最新候选检查通过后才能提交。保存采用完整版本快照，发布指向独立快照，因此失败、取消或后续编辑不会直接覆盖已发布内容。工具轨迹通过 SSE 展示并随消息保存。

技术栈为 Next.js 15、TypeScript、Tailwind CSS 3.4、Zustand 与 Vitest；InsForge 提供认证、Postgres、RLS、模型网关及托管。Agent 编排模块不依赖 Next.js，方便以后迁移执行环境。

主要取舍：

- **先支持小型纯前端应用。** 生成 HTML/CSS/JS，最多 6 个文件，不安装 npm 依赖、不生成后端，降低执行与部署复杂度。
- **生成代码只在沙箱 iframe 运行。** 不启用 `allow-same-origin`，模型没有主机终端、管理数据库或发布权限。应用存储由平台隔离桥接，不等于跨设备云同步。
- **SDK 管理循环，平台负责约束。** 授权、配额、工具权限、版本冲突及提交校验仍由应用控制；保留步数、时间和用量限制，避免无限循环。
- **分别记录生成完成与行为通过。** 服务端静态检查不证明按钮可用或业务正确；浏览器验收通过独立入口执行，结果绑定具体版本。
- **完整快照优先于存储压缩。** 历史读取和恢复更直接，代价是重复存储。开发时可使用 mock 降低费用，但真实模型能力必须另行验证。

## 当前完成程度

| 范围 | 当前状态 |
|---|---|
| 基础产品闭环 | 已实现并上线：账号、项目、生成、预览、继续修改、保存、版本恢复及公开发布 |
| 独立 ReAct Agent | 已上线：四角色独立 SDK 循环、按需委派、工具反馈修正、提交前校验、轨迹保存 |
| 工作台增强 | 已实现：错误报告与修复入口、文件引用、点选元素、版本 Diff、源码 ZIP、主题、Discover 与 Remix |
| 需求验收 | 已实现：版本绑定清单、有限浏览器动作检查、人工观察、父版本退化提示及带证据修复入口 |
| 工程保护 | 已实现：RLS、原子版本保存、幂等重放、并发冲突保护、额度与取消控制 |

**验证证据：**最近一次本地检查为 121 项测试、类型检查、lint 和生产构建通过。ReAct 迁移已有真实模型的新建、修改和静态错误修复冒烟，以及生产生成接口、持久化和幂等验证。2026-10-10 的简短线上 QA 中，已有计数器样本交互、刷新保留、代码与版本展示、公开页可用；四项浏览器自动检查全部通过，刷新后可读取新记录。

这些证据不等于当前版本的 PRD 全量回归通过：计数器是旧实验生成后导入的样本，并非这次 QA 新生成；本次没有重新测试发布操作，375px 视口设置未生效，移动端不计为通过。历史完整链路记录与本次 SDK 迁移验证应分开阅读。

**已知问题与待验收项：**

- 文件内容目前在完整工具参数校验后才分块推送，尚不满足严格的“随模型输出实时增长”；首段文字 3 秒内到达也缺少当前架构的测量证据。
- 浏览器文本断言可能包含隐藏子元素的文本，存在误判通过的风险。
- 创建项目与保存首条需求尚未组成单一事务；后者失败可能留下空项目。
- 新 ReAct 架构尚未完成十任务对照实验和完整浏览器回归。旧固定流水线的十任务结果为直接 Alex 10/10、团队 9/10，不能据此宣称多 Agent 或本次迁移提高了生成质量。

**暂未实现的扩展：**服务端自动浏览器修复循环、后台任务及断点续跑、生成应用的真实后端与依赖安装。Google 真实授权、原生手机输入法等也不在当前验收结论内。以上范围不会包装成已完成能力。

## 继续投入的方向与优先级

| 优先级 | 下一步 | 判断依据与完成标准 |
|---|---|---|
| 第一优先 | 修复验收误判、创建事务与代码增量展示 | 先保证结果可信、失败可恢复、等待过程可见；加入隐藏文本及消息写入失败反例，验证真实增量显示 |
| 第二优先 | 补齐当前架构的固定回归与十任务对照 | 用相同任务和独立断言比较直接 Alex 与团队；记录失败、成功率、耗时和 token，并补测首响应、连续生成和移动端 |
| 第三优先 | 将受限浏览器行为检查接入 Alex | 让修复依据真实点击和状态变化；限制动作、运行时间及重试次数，以行为通过率和原功能保留率判断收益 |
| 第四优先 | 按真实使用需求增加后台执行与恢复 | 长任务和断线成为主要失败来源时，再引入队列、检查点、恢复与可取消任务状态，避免过早增加运维复杂度 |

优先证明现有角色分工有效，再考虑更多角色、模型路由或更大的应用范围。新增能力应同时报告质量收益与时间、费用代价。
